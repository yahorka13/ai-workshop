# backend service

The reference TypeScript-on-Bun service. Read the root `AGENTS.md` first. This
service owns its manifest, generated lockfile, runtime, compiler, linter and
formatter configuration, tooling, tests and Dockerfile; it imports nothing from
another service.

It serves HTTP with Express: `GET /health` answers `{"ok":true}` while the
database answers `select 1` within 2 seconds and 503 `{"ok":false}` otherwise,
and GraphQL
runs on Apollo Server at `/graphql`. `src/app.ts` builds the app without
listening, so tests start it on an ephemeral port; `src/server.ts` reads the
configuration and listens; `src/index.ts` only calls it.

The GraphQL schema is code, built with Pothos on the one builder in
`src/graphql/builder.ts`. Each module in `src/graphql/resources/` defines one
resource: its object type, named after the file (`health.ts` defines
`Health`), with that resource's root fields. A type another resource nests is
imported from its own module, never defined beside the one that nests it.
`src/graphql/schema.ts` imports every resource module. `src/graphql/limits.ts`
refuses, while validating, an operation nested deeper than 8 levels or
selecting more than 100 fields (aliases and fragment spreads counted,
introspection exempt), with `extensions.code` `QUERY_TOO_COMPLEX`; raise a
limit in the change whose query needs it.

The backend's contract is `contracts/schema.graphql`, the sorted SDL of that
schema, generated by `src/contracts/` through `tooling/contracts.ts`; it is the
only thing another service may depend on. Regenerate it with
`bin/contracts generate` from the repository root (or
`bun run contracts:generate` here) and commit it with the change that caused
it; `bun run contracts`, the first gate of `bin/check`, fails when it is stale,
hand-edited or carries a file it did not generate. Root fields follow the
naming rule: a query is named after the resource it returns, with no verb
(`contact`, `contacts`), and a mutation starts with `create`, `update` or
`delete`. A field that cannot follow it is listed with its reason in
`NAMING_EXCEPTIONS` in `tests/support/naming.ts`. The schema is in alpha:
there is no deprecation, so change a field and every consumer in one change.

The UI calls the API from its own origin, `APP_URL` (a bare http(s) origin,
required: the backend refuses to start without it). `src/http/cors.ts`
answers CORS for exactly that origin, with credentials, and sends no CORS
header to any other; the session stack sets `APP_URL` to the slot's UI URL.

Validate every untrusted input (environment, request bodies, values read back
from libraries and the database) with a zod schema, never by hand.
Configuration is read once, in `src/config.ts`; an invalid variable stops
startup with its name and never its value.

Run all quality gates through `bin/check backend`; usage is in
`bin/check --help`. The `checks` Docker target installs frozen development
dependencies and runs at `/app` with Bun 1.4.3. The standard scripts are
`lint`, `format`, `typecheck`, `test:unit`, `test:integration`, `coverage`,
`duplicates`, `unused`, `imports`, `contracts` and `contracts:generate`.
`bin/check` runs contracts first, then lint, typecheck, coverage, duplicates,
unused and imports; coverage runs both
suites once, so use the two test scripts while iterating. Lint checks
formatting without writing; `format` rewrites.

`duplicates` fails on a block of at least 50 tokens and 5 lines that appears
twice in `src/`, `tests/` or `tooling/`; `.jscpd.json` sets that and is the
same in every service (`bin/tests/structure-config.test.sh`). Fix a clone by
extracting the shared code into one function or module, such as a helper in
`tests/support/`. A clone that must stay goes between
`// jscpd:ignore-start <reason>` and `// jscpd:ignore-end`, and raises this
service's count in `bin/duplicate-disables.txt` (`bin/check-disables.sh duplicates`).

`unused` fails on a file no entry point reaches, an export or exported type
no other file imports, and a dependency nothing uses. The `unused-rules`
block of `knip.config.ts` is the same in every service; the entry points
beside it are this service's. Delete what
is unused, or stop exporting what only its own file uses. An export that must
stay carries `/** @knipignore <reason> */`, and a dependency Knip cannot see
is listed in `ignoreDependencies` with `// knipignore: <reason>`; each raises
this service's count in `bin/unused-disables.txt`.

Mutation testing runs only in CI's `mutation` workflow, started by hand
(`gh workflow run mutation -R "$(bin/repo)"`), which runs
`bin/mutate backend` (usage in `bin/mutate --help`) in the Dockerfile's
`mutate` target, with `stryker.config.mjs` and both suites (not
the tests of tooling and gates). Do not run it while working. Two ignorers
keep mutants that are not behaviour out: `tooling/stryker-ignore-error-messages.mjs`
skips the texts of thrown Errors and Error subclass names (a `GraphQLError`'s
message reaches the client and stays mutated), and
`tooling/stryker-ignore-schema-definitions.mjs` skips the settings of a
`builder` call, which Pothos reads once per process and the contracts gate
pins; resolvers stay mutated. Kill a surviving mutant with a test that fails
on it; one that cannot change behaviour is marked on the line above it,
`// Stryker disable next-line <mutator>: <reason>`, and raises `backend` in
`bin/mutation-disables.txt`.

`imports` fails on an import cycle and on an import that breaks a layer rule
(`.dependency-cruiser.mjs`; its `import-rules` block is the same in every
service). The backend's layers:

- `src/graphql/` never imports `src/db/`: a resolver reaches data through a
  domain module such as `src/health.ts`.
- `src/http/` imports neither `src/graphql/` nor `src/db/`; `src/app.ts`
  wires them together.
- `src/db/` imports neither `src/graphql/` nor `src/http/`.
- Within `src/`, only `src/index.ts` imports `src/server.ts`.
- `src/` never imports `tests/` or `tooling/`.

Each violation prints its rule and how to fix it. A one-off exception is a
`pathNot` entry on the rule it breaks, with `// import-exception: <reason>` on
its line, and raises this service's count in `bin/import-disables.txt`.

Every test callback needs a direct, completed, non-snapshot assertion,
including aliased, conditional and parameterized tests with variable titles.
The policy (`tooling/test-policy.mjs`) applies to every code file under
`tests/`. Built-in matchers come from the pinned Bun runtime; a custom matcher
needs an explicit `additionalMatchers` allowlist on both local rules after its
behaviour is tested. Keep tests independent of external services and close
every listener a test opens.

Declare the narrowest true return type; never `unknown`, `object` or a wider
union to satisfy the return-type rule. Reach a maybe-missing value with
`defined`/`at` from `tests/support/defined.ts` in tests and `required` from
`src/required.ts` elsewhere, never `!` or `as`.

Coverage must represent every `src/` module and reach 100% of lines and
functions; every intentional exclusion in `bunfig.toml` needs a comment saying
why. Never edit coverage reports or the lockfile by hand: regenerate the
lockfile in the pinned image.

This service owns the database: the one migration history lives in `src/db/`,
and no other service applies DDL. It connects as the owner role in
`POSTGRES_USER` and `POSTGRES_PASSWORD`, to the database `POSTGRES_DB` at
`POSTGRES_URL` (`postgres://<host>[:<port>]`, never credentials or a path);
`src/db/connection.ts` is the one place that builds the connection. Change
`src/db/schema/`, then `bun run db:generate` to emit a migration folder,
`<timestamp>_<name>/` with its `migration.sql`, that is committed and reviewed.
Only the newest folder keeps a `snapshot.json`, a base of the whole schema that
the next migration is diffed against: `db:generate` writes it and deletes the
previous one, so never run `drizzle-kit generate` directly.
`bun run db:check` verifies the snapshot, `bun run db:verify` additionally
fails on a malformed folder, a second snapshot, or committed migrations that no
longer describe the schema module, and `bun run db:migrate` applies the
history, in folder-name order, under an advisory lock. Usage is in
`bun run db:migrate --help`. Never run `drizzle-kit push`: it diffs a live
database with no recorded migration (`bin/check-migrations-expand-only.sh`
fails on one). There are no down migrations, so every migration is expand-only:
a step that drops, renames or retypes needs a `-- contract: <reason>` comment.
A committed migration is never edited (`bin/check-migrations-immutable.sh`),
and generated SQL and snapshots are never edited by hand.

Migrations run at startup: the runtime image applies the history and then execs
the server, and a failure stops the container before it listens. The runner
holds a Postgres advisory lock while applying, which makes several replicas
safe: one applies, the rest block and then find the history current. Drizzle's
migrator takes no lock, so that lock is ours and load-bearing: do not remove
it.

Migrations are named by timestamp, so parallel branches do not collide on a
folder name. They still collide on the one snapshot: two branches that each
generate from the same parent each move it into their own new folder, so
merging one into the other is a rename/rename conflict on `snapshot.json`, and
a history committed with both snapshots fails `bun run db:verify`. To resolve,
while merging the base into your branch: resolve `src/db/schema/` as usual,
delete your own migration folder, take the base's migrations with
`git checkout <base> -- src/db/migrations`, and run `bun run db:generate`
again, so your migration is diffed against the merged schema and the snapshot
moves into it; the SQL comes back from your schema module, so nothing is lost.

The `runtime` Docker target installs production dependencies only, runs as
`bun` and is the image the stack runs. Start or rebuild it with `bin/up`;
container commands run at `/app`, for example
`bin/compose exec backend bun --version`.

To add another service like this one, copy its owned files, change the package
name and the service-specific code and rules, regenerate its lockfile in the
pinned Bun image, and add one job calling the reusable service-check workflow
with the service folder name. Nothing in `bin/check` needs to change.
